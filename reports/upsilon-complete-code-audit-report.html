1. Executive Summary

The repository contains two React/Vite applications: the public company website and the employee workspace. A shared Express/Mongoose backend provides employee, leave, reimbursement, notification, profile, team, holiday, Careers, and public website APIs. A separate legacy company website server also remains in the repository.

Build healthBoth React production builds pass.
Backend syntaxAll backend JavaScript files pass node --check.
Confirmed critical issuesNo confirmed RCE or destructive data-loss issue.
CorrectionsSecurity, authorization, data integrity, email, uploads, integration, and polling fixes applied.

The most important corrected problems were client-controlled reimbursement totals, invalid repeated reimbursement state transitions, public résumé exposure, inactive users retaining API access, role-attribution spoofing in leave status changes, known seed passwords, and missing reimbursement approval email to the applicant.

3. High-Priority Issues Corrected

HIGHReimbursement amount manipulation

Problem: The backend accepted subtotal and totalReimbursement supplied by the browser.

Impact: An applicant could alter a network request and submit a value that did not match the expense items.

Fix: Every item, cost, date, business purpose, and cash advance is validated. Subtotal and final reimbursement are recalculated server-side.

HIGHInvalid and repeatable reimbursement transitions

Problem: TL, Manager/HR, and Finance endpoints did not consistently verify the current workflow state.

Impact: Requests could be approved or rejected repeatedly, generating duplicate history, email, and notifications. Finance could mark an invalid claim paid.

Fix: Added pending-state checks at each stage. Finance can mark paid only when the claim is finally approved and awaiting payment.

HIGHInactive accounts retained access

Problem: JWT middleware loaded the user but did not reject isActive: false.

Impact: A deactivated user with an existing cookie remained authorized until token expiry.

Fix: Protected routes now return 403 immediately for inactive users.

HIGHCandidate résumés were public

Problem: Résumés were served from guessable /uploads/resumes/... URLs.

Impact: Anyone who obtained or guessed a filename could access candidate personal information.

Fix: Public résumé paths now return 404. Careers admins download through authenticated GET /api/applications/:id/resume.

HIGHKnown privileged seed passwords

Problem: Admin, Finance, and Careers-admin scripts contained default passwords.

Impact: Running those scripts could create predictable privileged credentials.

Fix: Seed scripts require environment-provided passwords of at least eight characters. A repository scan found zero remaining known default-password matches.

HIGHApprover identity could be mislabeled

Problem: A Manager could choose “Approved by HR” and HR could choose “Approved by Manager” in manual status management.

Impact: Audit history and final status could misrepresent who made the decision.

Fix: The backend and frontend now expose only statuses attributable to the authenticated role.

4. Medium-Priority Issues Corrected

  • Only Employee and Team Leader roles may submit leave or reimbursement requests.
  • Final reimbursement approval now emails the applicant; rejection continues to email once.
  • Reimbursement submission recipients are deduplicated and missing addresses are skipped.
  • TL reimbursement rejection wording now clearly says “not recommended” and explains that Manager/HR makes the final decision.
  • Career applications validate email addresses and allow only HTTP/HTTPS LinkedIn and portfolio links.
  • Duplicate applications for the same job and email return HTTP 409.
  • Email HTML now escapes user-controlled values, including names, purposes, statuses, and rejection reasons.
  • Signature previews no longer hardcode localhost. Local /uploads requests are proxied by Vite.
  • Signature upload is image-only and limited to 5 MB.
  • Finance frontend routes now require authentication.
  • Team listing is Admin-only at the backend.
  • Production global 500 responses no longer expose internal error messages.
  • The legacy website server no longer prints SMTP configuration values.
  • Notification read attempts return 404 when the record is missing or not owned by the requester.
  • The company website sticky contact button previously rendered nothing; its existing intended UI is restored.
  • Finance leave search now reads the backend’s actual finalStatus property.

5. Authentication and Role Audit

Actual workspace roles are Admin, HR, Manager, TeamLeader, Employee, and Finance. Backend role checks are authoritative for the active Admin, leave, reimbursement, Finance, holiday, and team-management APIs.

Login normalizes email, compares a bcrypt hash, rejects inactive accounts, issues a seven-day HTTP-only JWT cookie, and avoids returning the password hash. Password changes validate the current password and require at least eight characters.

Remaining authentication/security concerns

  • CSRF: Production authentication cookies use SameSite=None, but there is no CSRF-token mechanism.
  • Rate limiting: Login, contact, resource-download, and public application endpoints have no brute-force or spam throttling.
  • Several older controllers still return raw error.message values directly.
  • Concurrent approval requests are protected by state checks but not by an atomic compare-and-update database operation.

6. Leave Workflow

  1. An Employee submits leave. The assigned Team Leader, assigned Manager, and active HR users are notified and emailed.
  2. The Team Leader records an advisory approval or non-recommendation. This is not a final decision.
  3. The assigned Manager or HR makes the final approval/rejection under the existing alternative-final-approver design.
  4. The applicant receives the in-app notification and final decision email.
  5. Approved leave continues to notify and email Finance.

A Team Leader applying for personal leave skips TL self-review and proceeds to Manager/HR. Edited approved leave enters reapproval. Final email is not sent for intermediate TL action.

Concern left unchanged: The manual status endpoint can still place a request into a final state without reproducing every Finance side effect of the dedicated approve handler. Removing that capability could alter intended business behavior, so only role attribution was corrected.

7. Reimbursement and Finance Workflow

  1. Employee or Team Leader submits a validated claim.
  2. The server calculates monetary values from expense items.
  3. TL review is advisory for Employee claims.
  4. Manager or HR makes the final decision.
  5. Applicant receives in-app and email notification.
  6. Approved claims are routed to active Finance users.
  7. Finance can mark paid only from the approved/pending-payment state.

Email failures are caught after database decisions and do not roll back successful workflow state.

14. Remaining Issues

  • Workspace lint baseline is still non-clean.
  • No automated unit, integration, or end-to-end tests are configured.
  • The company package’s standalone development command starts the legacy server, which lacks newer Careers APIs. The shared backend is required for complete functionality.
  • Cloudinary files may become orphaned when upload succeeds but later controller validation fails.
  • CSRF protection and public/auth rate limiting remain absent.
  • Some controllers expose raw internal error messages.
  • Approval transitions are guarded but not atomic against simultaneous duplicate requests.
  • Dashboard statistics return broad organization totals; the intended role visibility was not clear enough to change safely.
  • Legacy/current Careers implementations should eventually be consolidated.
